# Frontend Data Models

This document describes the data contracts the frontend expects from local files, a future backend, or a CMS. Current implementations live behind async domain functions in `lib/content/site.ts`, `lib/content/posts.ts`, `lib/content/projects.ts`, `lib/content/notes.ts`, and `lib/content/workbench.ts`. Those functions delegate to `ContentSource`, so backend or CMS integration should replace source configuration before changing page components.

## Fetch Wrapper

All read-only content requests should go through `lib/content/fetch-wrapper.ts`.

Environment variables:

```env
# Direct backend access from Next SSR.
CONTENT_API_BASE_URL=http://localhost:8080/api

# Or root-relative reverse proxy access. The wrapper resolves this to an absolute
# server URL before calling fetch during SSR.
CONTENT_API_BASE_URL=/api

# Optional when CONTENT_API_BASE_URL is root-relative. Defaults to
# NEXT_PUBLIC_SITE_URL, VERCEL_URL, then http://localhost:3000.
CONTENT_API_ORIGIN=http://localhost:3000

# Required by POST /api/revalidate.
REVALIDATE_SECRET=replace-with-a-long-random-token
```

Examples:

```ts
fetchWrapperOrMock("/posts", mockPosts, { revalidate: 300 })
fetchOptionalWrapperOrMock(`/posts/${slug}`, mockPost, { revalidate: 300 })
```

If `CONTENT_API_BASE_URL` is not configured, the domain functions read local JSON and Markdown files through `fileSource`. Once it is configured, the same functions call the backend through `apiSource` while preserving Next.js `fetch` caching and ISR options.

## Publishing Cache Strategy

The frontend should use Next.js server-side `fetch` caching plus on-demand revalidation. Public content pages are SSR/ISR by default: the first request renders from backend data, then Next.js caches the result until the configured `revalidate` window expires or a webhook invalidates the matching cache tags.

Recommended cache tags:

```ts
type ContentCacheTag =
  | "site"
  | "home"
  | "introduction"
  | "posts"
  | `post:${string}`
  | "projects"
  | "notes"
  | "workbench"
  | "sitemap"
```

Recommended tag mapping:

| Domain function | Cache tags | Revalidate |
| --- | --- | --- |
| `getHomePageContent()` | `site`, `home` | 600 |
| `getIntroductionPageContent()` | `site`, `introduction` | 600 |
| `listPosts()` | `posts` | 300 |
| `listPostSlugs()` | `posts`, `sitemap` | 300 |
| `getPostBySlug(slug)` | `posts`, `post:{slug}` | 300 |
| `listRelatedPosts(slug)` | `posts`, `post:{slug}` | 300 |
| `listProjects()` | `projects` | 600 |
| `listNotes()` | `notes` | 300 |
| `listWorkbenchItems()` | `workbench` | 600 |
| `listWorkbenchActivity()` | `workbench` | 300 |

Backend notes:
- Backend content mutations should trigger frontend revalidation after the write transaction commits.
- The backend does not need to know Next.js internals. It only needs to send affected `tags` and `paths`.
- Use tag revalidation for data dependencies and path revalidation for route output. For example, publishing a post should invalidate both `post:{slug}` and `/blog/{slug}`.
- Do not expose revalidation without authentication. The frontend route must require a shared secret or signed webhook.

## Dynamic Sitemap

The sitemap is generated by `app/sitemap.ts` and should remain server-side. It should call domain functions instead of importing static arrays directly.

Current and recommended route coverage:

| Route | Source | Included now | Notes |
| --- | --- | --- | --- |
| `/` | static route | yes | `lastModified` can use homepage content update time later. |
| `/blog` | static route | yes | List page for posts. |
| `/blog/:slug` | `listPosts()` | yes | `lastModified` comes from post date or backend `updatedAt`. |
| `/projects` | static route | yes | Add project detail URLs only if project detail pages exist. |
| `/notes` | static route | yes | Add note detail URLs if notes become shareable pages. |
| `/workbench` | static route | yes | No detail page currently. |
| `/introduction` | static route | yes | Page singleton. |

Recommended sitemap settings:

```ts
export const revalidate = 300
```

Backend notes:
- Prefer returning `updatedAt` for posts, projects, and notes. If unavailable, the frontend falls back to `date`.
- Hidden, draft, scheduled, or private content must not appear in sitemap responses.
- If the backend supports locales later, sitemap entries should include alternate language links.

## LLM And GEO Files

The site exposes LLM-friendly markdown/text resources for generative engine optimization and agent retrieval.

Industry references:
- `llmstxt.org` proposes a root `/llms.txt` markdown file with one H1, a blockquote summary, H2 file-list sections, and optional links.
- Stripe and Vercel expose curated `llms.txt` indexes with links to markdown documentation and full-context files.
- Cloudflare uses `llms.txt` as a top-level directory that links to narrower product-level `llms.txt` files.
- Feishu Open Platform uses `/llms.txt` as a concise platform overview plus links to topic-specific `.txt` documents.

Implemented files:

```txt
/llms.txt
/llms-full.txt
/blog/:postSlug.md
```

Implementation files:

```txt
lib/llms.ts
app/llms.txt/route.ts
app/llms-full.txt/route.ts
app/blog-md/[postSlug]/route.ts
next.config.mjs rewrite from /blog/:postSlug.md to /blog-md/:postSlug
```

Format strategy:
- `/llms.txt` is a short curated index. It follows the common convention: one H1, a blockquote summary, then H2 sections with markdown link lists.
- `/llms-full.txt` contains expanded site content for larger context windows, offline indexing, or vectorization.
- `/blog/:postSlug.md` exposes a clean markdown version of each article, so LLMs do not need to parse the HTML page.
- The `Optional` section in `/llms.txt` is used for lower-priority content such as lab notes and workbench updates.

Backend notes:
- Do not store these files manually. They are generated from the same domain functions used by pages.
- Publishing a post, project, note, workbench item, homepage, or introduction page should revalidate `/llms.txt` and `/llms-full.txt`.
- Publishing a post should also revalidate `/blog/:postSlug.md`.
- Draft, private, scheduled, or internal-only content must not appear in LLM files.
- If article slugs change, revalidate both the old and new `.md` paths.
- Keep `/llms.txt` concise. Put full article bodies in `/llms-full.txt` and per-article `.md` files.

## RSS Feeds

The site exposes separate RSS feeds for long-form blog posts and casual notes:

```txt
/rss.xml
/notes/rss.xml
```

Both feeds are generated from the same domain content layer as the pages:

- `/rss.xml` reads `getProfileContent()` and `listPosts()`.
- `/notes/rss.xml` reads `getProfileContent()` and `listNotes()`.
- Site name, owner, email, and description come from `content/site/profile.json` or the CMS/API source behind `getProfileContent()`.
- Blog and note entries remain draft-filtered because they use `listPosts()` and `listNotes()`.

Runtime behavior:

- Feed routes use ISR with `revalidate = 300`.
- File-source changes are reflected after restart or rebuild in local/offline mode.
- API/CMS changes can update feeds immediately through `/api/revalidate`.

Recommended webhook payloads:

```json
{ "type": "post", "slug": "my-post-slug" }
```

Revalidates `/rss.xml` plus the affected blog page and generated artifacts.

```json
{ "type": "note", "slug": "my-note-slug" }
```

Revalidates `/notes/rss.xml` plus the notes index and generated artifacts.

```json
{ "type": "profile" }
```

Revalidates both RSS feeds when site name, owner, email, or description changes.

## Dynamic Open Graph Images

Static OG images are acceptable for generic pages, but article pages should use dynamic OG images so the title, category, and author stay in sync with content.

Recommended frontend files:

```txt
app/opengraph-image.tsx
app/(public)/blog/opengraph-image/route.tsx
app/(public)/blog/[postSlug]/opengraph-image/route.tsx
app/(public)/projects/opengraph-image/route.tsx
app/(public)/notes/opengraph-image/route.tsx
app/(public)/workbench/opengraph-image/route.tsx
```

Recommended article OG data contract:

```ts
interface OpenGraphPostData {
  slug: string
  title: string
  excerpt: string
  category: string
  tags: string[]
  author: {
    name: string
    avatar?: string
  }
  date: string
}
```

Frontend notes:
- Use Next.js `ImageResponse` for dynamic 1200x630 images.
- The article metadata should reference the generated route, for example `/blog/my-post/opengraph-image`.
- OG image generation should read the same content source as the page. Do not create a second backend contract just for OG unless the rendering becomes expensive.
- If OG images become expensive, add `revalidate` or use cache tags matching the underlying content, such as `post:{slug}`.

## Webhook Revalidation

The frontend should expose one authenticated revalidation endpoint:

```txt
POST /api/revalidate
Authorization: Bearer <REVALIDATE_SECRET>
```

Request body:

```ts
interface RevalidateRequest {
  type:
    | "site"
    | "home"
    | "introduction"
    | "post"
    | "project"
    | "note"
    | "workbench"
    | "sitemap"
    | "custom"
  slug?: string
  tags?: string[]
  paths?: string[]
}
```

Example post publish payload:

```json
{
  "type": "post",
  "slug": "nextjs-cache-strategy",
  "tags": ["posts", "post:nextjs-cache-strategy", "sitemap", "llms"],
  "paths": [
    "/blog",
    "/blog/nextjs-cache-strategy",
    "/blog/nextjs-cache-strategy.md",
    "/sitemap.xml",
    "/llms.txt",
    "/llms-full.txt"
  ]
}
```

Example homepage update payload:

```json
{
  "type": "home",
  "tags": ["site", "home"],
  "paths": ["/"]
}
```

Expected frontend behavior:

```ts
revalidateTag("posts", "max")
revalidateTag(`post:${slug}`, "max")
revalidatePath("/blog")
revalidatePath(`/blog/${slug}`)
revalidatePath(`/blog/${slug}.md`)
revalidatePath("/sitemap.xml")
revalidatePath("/llms.txt")
revalidatePath("/llms-full.txt")
```

Backend notes:
- Call the webhook only after the database write and any publish-state transition succeeds.
- Retry on non-2xx responses with a short backoff. Revalidation is important but should not block content persistence forever.
- Include enough data for the frontend to invalidate specific paths. For slug changes, send both the old and new paths.
- Draft updates usually should not revalidate public paths unless the draft was previously published.
- For bulk imports, send coarse tags such as `posts` and `sitemap` instead of one webhook per item.

Recommended webhook response:

```ts
interface RevalidateResponse {
  revalidated: boolean
  tags: string[]
  paths: string[]
  now: string
}
```

## Post

Used by `/blog`, `/blog/[postSlug]`, sitemap, Open Graph metadata, JSON-LD structured data, related posts, categories, and tags.

```ts
interface BlogPost {
  id: number | string
  slug: string
  title: string
  excerpt: string
  thumbnail?: string
  content: string
  date: string
  updatedAt?: string
  readTime: string
  category: string
  tags: string[]
  author: {
    name: string
    avatar: string
    role: string
  }
  featured: boolean
  draft?: boolean
  color: string
}
```

Backend notes:
- `slug` must be unique and stable because it is used as the route key.
- `content` is currently markdown source and is rendered server-side with `react-markdown`, `remark-gfm`, and `rehype-sanitize`.
- Prefer returning markdown, not arbitrary HTML. If the backend returns HTML later, it must be sanitized before rendering and the frontend renderer should be reviewed again.
- `date` must be parseable by `new Date(date)` because metadata and sitemap use ISO dates.
- `updatedAt` should be returned when available and is preferred for sitemap `lastModified` and metadata `dateModified`.
- `draft: true` must never be returned by public list/detail endpoints.
- `excerpt`, `title`, `author`, `tags`, and `category` are required for SEO metadata.
- `color` is a presentation hint. It can remain frontend-owned if the backend should not store Tailwind classes.

Recommended backend endpoints:
- `GET /posts` returns published post summaries or full posts for listing.
- `GET /posts/slugs` returns `{ slug: string }[]` for static path generation.
- `GET /posts/:slug` returns one full post.
- `GET /posts/:slug/related?limit=3` returns related post summaries.
- `GET /post-categories` returns `{ slug, name, count }[]`.
- `GET /post-tags/popular?limit=10` returns `string[]`.

## Project

Used by the homepage project section and `/projects`. Project filtering is server-rendered from URL query params: `status`, `query`, and repeated `tag`.

```ts
type ProjectStatus = "shipped" | "in-progress" | "archived"

interface Project {
  id: number
  title: string
  description: string
  tags: string[]
  status: ProjectStatus
  year: string
  stars: number
  forks: number
  url: string
  homepage?: string
  featured: boolean
  highlight?: boolean
}
```

Backend notes:
- `url` should be the canonical source URL, usually GitHub.
- `stars` and `forks` should be backend-cached from GitHub instead of fetched by the browser.
- `featured` and `highlight` control frontend placement and visual emphasis.
- `status` should use the exact enum values above unless the frontend status union is expanded.

Recommended backend endpoints:
- `GET /projects` returns all public projects and may accept `status`, `query`, and `tag`.
- `GET /projects/statuses` returns available statuses plus `all` if the backend owns filter options.
- `GET /projects/tags` returns available tags.
- Optional: `POST /internal/github-sync/projects` updates `stars`, `forks`, and recent activity on a schedule.

## Interaction Backend Models

Interactive writes are intentionally separate from read-only content. The first Node backend owns these models with SQLite.

### Message

Used by `/contact` and later by newsletter or lightweight inquiry forms.

```ts
interface MessageInput {
  name: string
  email: string
  subject?: string
  body: string
  source?: "contact-page" | "newsletter" | "blog-sidebar" | "footer" | "custom"
}

interface Message {
  id: number
  name: string
  email: string
  subject: string
  body: string
  source: string
  status: "new" | "replied" | "archived"
  createdAt: string
  updatedAt: string
}
```

Implemented endpoint:

```txt
POST /messages
```

Behavior:
- Validates input with `zod`.
- Stores the message in SQLite.
- Creates a reply token.
- Sends owner notification email with `reply_url`.
- If SMTP is missing, returns `503` with the missing variables and still includes the stored message id.

### ReplyToken

Reply URLs let the site owner reply without a login UI in the first version.

```ts
interface ReplyToken {
  id: number
  token: string
  targetType: "message" | "comment"
  targetId: number
  expiresAt: string
  usedAt?: string

```

Implemented endpoints:

```txt
GET /reply/:token

```

Behavior:
- Token is HMAC signed with `REPLY_TOKEN_SECRET`.
- Token is also stored server-side, so it can expire or be marked used.
- `GET /reply/:token` returns a small HTML reply form.
- `POST /reply/:token` sends email to the original visitor and marks the token used.

### Notification

Tracks owner notification attempts.


Notification order:

- Feishu webhook is optional when `FEISHU_WEBHOOK_URL` is configured.

## Rendering Boundaries

SSR/SSG data:
- Site profile, navigation, homepage copy, and introduction page content.
- Blog list and post detail content.
- Project list and filtered project result pages.
- Notes and workbench summaries if those pages should be SEO-visible.
- Metadata, canonical URLs, Open Graph fields, JSON-LD, and sitemap entries.

Client islands:
- Hero typewriter animation.
- Header mobile menu, scroll styling, and theme controls.
- Blog sidebar search, category selection UI, and newsletter form.
- Blog share/copy/scroll actions.
- Project filter controls that update URL query params.
- Expandable note cards, bookmark actions, and any live refresh controls.
